## 技能库没有持续形成新策略

十次整理中仅两次产生实际变更：3300 把空库写成四条通用建议，3307 对同样四条补充了初始 no_contact、非上升平台和终止处理。另四次接受但不变，四次拒绝；没有持续增长或替换可执行的数值策略。

3301–3307 输入库的哈希完全相同，因此这一段并没有逐次改变技能内容。3307 的 6/6 发生在该组结束后的技能更新之前，不能把这次表现归因于随后发生的更新；3308、3309 才使用更新版，两组均为 5/6。

3301、3304、3309 的提案分别包含 643、624、646 字符的 practice，超过 600 字符限制；3306 改了条目却未附公开 event_id。程序按设计保留旧版，未静默放宽限制。因此“每次都调用 API”不等于“每次都成功更新”。

多数内容重述固定任务 prompt 已有的接近、稳定、释放和 OOD 规则，缺少与具体动作参数、接触阶段和公开结果相连的可检验策略。固定 YAML prompt 本身约 15405 字符，包含既有控制先验；零起点仅指跨 episode 的外部技能库与键位缓存。

## 3302 的 0/6 是释放代码问题

该组第二至第六音都有原生 press 事件，说明已通过按下角度、真实力容差及保持规则，但均没有 release 事件。生成的 `_release()` 仅发送三次 action，每次四物理步，共 0.05 秒，然后立即调用 `finish_piano_note_attempt()`。原生需要释放角度不高于 0.008 rad 持续 0.10 秒；这三步连最短持续时间都不够。

公开动作审计同时显示，提交尝试时实际食指弯曲仍约 0.369–0.371 rad，虽然最后一次目标已是 0 rad；实际手腕也尚未到 0.04 m 悬停目标。这里明显把“发出释放目标”当成了“实际完成释放”。这属于模型生成策略错误，而不是深度力估计本身导致的五音失败。第一音未出现原生 press，需另按未达成按下条件处理。

## 其余失败主要是保持与估计有效性

除 3302 的释放问题外，失败音均为重音且没有原生 press。逐物理步目标力连续达标最长为 0–23 步，低于 0.12 秒所需的 29 步；其中 3300 的 C#4 重音在 OOD 后安全退出，目标力区间连续步数为零。没有 wrong_key 或 wrong_note_force 判罚。

查询时刻、age=0、quality=ok 且真实力至少 0.05 N 的逐组 MAE 约 0.005–0.013 N。这一口径排除了 OOD，并且不覆盖动作之间的物理步，不能证明全部接触状态已标定可靠。3307 的三次重音自报 hold_confidence=False，却原生通过，也进一步说明自报保持信心与官方判分没有充分对齐。

## 整理输入存在明确缺口

实际发给整理模型的每组仅 31–45 条公开事件，类型都是稀疏 force_estimate、attempt_finalized 和 code_execution。虽然原始公开日志含全部 action 行，现有筛选器没有保留任何 action 行；force 事件里的手部状态主要来自按压查询，也不能补齐释放后的执行状态。因此整理模型看不到完整的实际释放时序，只能结合代码和 uncertain 自报摘要推断原因。

真实力、原生判分未送入整理模型，边界保持正确；但要改善策略，还需要从允许的公开实际状态构建按压、释放和终止的可核查摘要，不能指望模型从缺失的反馈中自行恢复私有失败原因。

## 如何判断模型作用

本轮模型配置是 gpt-6-sol，十条程序均可执行并走完六次尝试，没有语法或基础设施错误。但 3302 的释放、以及其按力上升而非停止上升来累计稳定性的判断，表明存在明显的逻辑与指令遵循错误。模型质量是因素之一；尚未用相同 prompt、相同输入记忆和相同种子做模型对照，不能把所有问题归因于模型强弱或接口本身。

先修复整理输入遗漏和可客观检查的动作完成条件，使技能能保存带来源的动作策略与公开结果；格式超长或缺来源的更新可在明确记录成本的条件下安排一次限定纠正。之后再以固定 seed、固定初始库和相同上下文比较模型，才有条件评估换模型的收益。此处是后续建议，本轮没有实施这些控制或整理修改。

前五组与后五组平均生成动作数分别为 1089.4 和 1137.4，未下降；不同 seed 难度、一次采样与库变化混杂，不能把该变化解释为因果效果。
